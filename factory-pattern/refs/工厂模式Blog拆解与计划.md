### 1.2 log 拆分方案的 4 个问题

log 主张拆 5 篇。把它映射回 source 章节后，暴露以下问题：

**问题 1：切分不自洽，第 2 篇会超载。**
log 的第 2 篇《简单工厂、工厂方法、抽象工厂》要吞下 §3 + §4 + §5 + §6 共 **4 章**，反而是全系列最长的一篇，与 log 自己那句"掘金读者对长文的耐心有限"直接冲突。

**问题 2：§6 没有明确归属。**
§6 讲的是"上层结构 / 组合根 / 注册表 / 取舍表"，语义上属**装配**而非**层次关系**。按 log 的分法，它要么被硬塞进第 2 篇（臃肿），要么掉进第 4 篇 DI（主题错位），两边都不对。

**问题 3："每篇加一个可运行例子"执行成本高且割裂。**
5 篇各写一个独立 `main`，读者要在 5 个工程之间跳，作者要维护 5 份脚手架。应改为**共享一个 repo，各篇只增量提交该篇的 `.cpp`**。

**问题 4：把"缺生产级手册"当缺陷，是诉求错位。**
测试 / 异常安全 / 线程安全 / ABI 是"生产级手册"的指标。log 自己也说这份素材是"进阶地图"而非"手册"。正确做法是**在系列开篇声明边界**，而不是把 5 篇硬撑成手册。

### 1.3 log 漏掉的 2 个 source 亮点 + 1 个共同盲区

**亮点 A：§7.2 `unique_ptr` 返回机制。**
source 明确澄清了三件事：靠**模板转换构造 + 向上转型**；`return` 局部 `unique_ptr` 时编译器**自动隐式移动，不用写 `std::move`**；**完美转发（`std::forward`）在此没有参与**。
这是最容易被人讲错的细节，值得单独立小节。log 的价值清单里完全没提。

**亮点 B：§9.6 Nginx（C 语言里的工厂变体）。**
用函数指针结构体 `ngx_event_actions_t` 充当"抽象接口"，初始化时赋值 `ngx_event_actions = ngx_epoll_module_ctx.actions;` 完成"把创建决策推迟到运行时"。这是全系列**唯一的跨语言视角**，最能体现"模式与语言无关"。log 只在"开源案例对照"里一笔带过。

**共同盲区：§10 的 7 项待展开，双方都没做归属映射。**
log 只说"变成下篇预告"，但 7 项预告各挂到哪篇、哪些**应当就地补齐而不是预告**，都没说清。实际其中 2 项（10.6、10.7）必须在本系列内补齐，否则系列自身不完整。

## 二、重组后的 Blog 章节

**总原则**：把 source 的"知识清单结构"改成"读者问题结构"。一条主线贯穿——**从"为什么需要工厂"到"什么时候不该用工厂"**。

系列定名：**《C++ 工厂模式，从 if/else 到生产级》**

### 第 1 篇《为什么你的 C++ 代码里到处都是 if/else new》
- **一句话**：直接 `new` 的四个问题 → 工厂的诞生
- **承接素材**：§1、§2.1–§2.4
- **论证链**：类型分支膨胀 → 调用方知道所有具体类 → 构造变化波及所有调用点（§2.3）→ 编译依赖变重（§2.4）→ 解耦创建与使用
- **必须新增**：一份可编译的最小对照（naive 版 vs factory 版，同一份 `main`，跑出同一结果）
- **图**：before/after 依赖关系图（新增）
- **字数目标**：2500–3500

### 第 2 篇《简单工厂、工厂方法、抽象工厂：不是三个并列模式》
- **一句话**：GoF 只承认两个；简单工厂是 idiom；三者在一条演化线上
- **承接素材**：§3.1–§3.3、§4.1–§4.5
- **核心论点**：抽象工厂 = 多个工厂方法 + **产品族配套约束**（不是简单的"工厂方法集合"）
- **必须新增**：三份同一 Logger 场景的可编译代码；一屏对比表沿用 §4.5 并补一列"何时选哪个"
- **图**：层次关系图（沿用 §3.2）
- **字数目标**：3000–4000

### 第 3 篇《抽象工厂实战：业务场景、组合根与自注册》
- **一句话**：产品族一致性 → 组合根 → 注册表消除 if/else → 取舍
- **承接素材**：§5.1–§5.6、§6.1–§6.4
- **核心论点**：抽象工厂不承诺消灭对具体类的引用，只承诺把它限制在组合根（§6.2）
- **必须新增**：一个完整的"支付渠道"可运行 demo（含 `PaymentFactoryRegistry` + 自注册）
- **图**：组合根结构图（沿用 §6.2）、注册表创建时序（新增）
- **字数目标**：3000–4000

### 第 4 篇《C++17 之后，工厂模式发生了哪些变化》
- **一句话**：6 个变化 + 1 张踩坑表
- **承接素材**：§7.1–§7.8
- **核心论点**：运行时多态仍是默认；模板 / 编译期工厂是局部优化，不是替代
- **必须新增**：
  - 把 §7.2 拎出单独立小节（`unique_ptr` 返回机制三问：怎么转型、要不要 `std::move`、`std::forward` 到底参不参与）
  - **踩坑清单表**：静态初始化顺序、链接器丢弃未被引用的 `.cpp`、`unique_ptr` 转换构造、自注册的调试可见性
- **图**：变化总表（沿用 §7.8）
- **字数目标**：3500–4500

### 第 5 篇《工厂和依赖注入，到底谁管什么》
- **一句话**：工厂答"`new` 哪个、怎么 `new`"；DI 答"谁需要它、怎么给它"
- **承接素材**：§8.1–§8.7、补做 §10.6
- **核心论点**：服务定位 ≠ 依赖注入；组合根同时使用工厂和 DI
- **必须新增**：§10.6 就地补齐——组合根 + 工厂 + DI + 单元测试替换的完整小例子
- **图**：职责对比表（沿用 §8.2）
- **备注**：**全文最易出圈的一篇，建议用作系列破圈首发**
- **字数目标**：2500–3500

### 第 6 篇《从 Fast DDS 到 Cyber RT：开源项目里的工厂模式》
- **一句话**：6 个真实项目，看模式在不同层次的形态
- **承接素材**：§9.1–§9.7
- **核心论点**：生产级项目对工厂是**克制**的——Fast DDS 只有简单工厂，Cyber RT 才上自注册 + 动态库
- **结构建议**：按"形态复杂度"排序（简单工厂 → 工厂方法 → 工厂方法+自注册 → 抽象工厂 → C 变体），最后以 §9.6 Nginx **压轴**
- **必须新增**：补足深度不均——Thrift 从骨架补到"配套一致性的具体体现"（§10.5）；Cyber RT 补 `ClassLoader` 引用计数（§10.3）
- **图**：Cyber RT 创建时序（沿用 §9.3）、案例对比总表（沿用 §9.7）
- **字数目标**：4000–5000

### 第 7 篇《什么时候不该用工厂：过度设计的信号》
- **一句话**：只讲怎么用、不讲什么时候不用，就是误导人
- **承接素材**：§8.6、§8.7、补做 §10.7
- **核心论点**：`make_unique<T>()` 里没有选择逻辑的"工厂"不是工厂；一个实现配一个 DI 容器就是过度设计
- **必须新增**：§10.7 就地补齐——正反案例对照（该用 vs 不该用）
- **字数目标**：2000–3000
- **备注**：篇幅紧时，可与第 5 篇合并为"边界篇"的尾部

### 系列级约束（贯穿 7 篇）
1. **共享一个可编译 repo**：第 1 篇建骨架，后续每篇只增 `NN_xxx.cpp`。
2. **开篇声明边界**：明确本系列是"进阶地图"不是"生产级手册"，测试 / 线程安全 / ABI 只做清单不做展开。
3. **每篇结尾做下篇预告**：把 §10 的待展开项明确挂账（映射见第三节）。
