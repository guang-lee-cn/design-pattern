# 001 · 一个 C++20 才生效的规则，被写成了 C++11 起就有

- **日期**：2026-09-20
- **落点**：第 4 篇《C++17 之后，工厂模式发生了哪些变化》§7.2
- **性质**：事实性错误（不是笔误），由编译器发现

## 症状

配套工程第一次全量构建时，`code/src/04_modern_cpp17/probe_unique_ptr.cpp` 编译失败：

```
error: use of deleted function
  'std::unique_ptr<...>::unique_ptr(const std::unique_ptr<...>&)'
   81 |     return incoming;
```

## 原稿的说法

正文（对照表 + 标准演进段）和代码注释三处都在讲同一件事：

> 按值传入的函数参数，返回时会**隐式移动**，所以既不需要 `std::move` 也不需要 `std::forward`。

## 实际情况

这句话在 **C++20 之前是错的**。

| 标准 | `[class.copy.elision]` 对隐式移动候选的措辞 | `return incoming;` 的结果 |
|---|---|---|
| C++11 / 14 / 17 | 候选是局部对象，**"other than a function or catch-clause parameter"** | 函数参数被**显式排除** → 走拷贝 → `unique_ptr` 编译失败 |
| C++20（P1825R0） | 删除上述排除 | 同一行代码合法 |

即：**同一行代码，C++17 编不过，C++20 编得过。**

## 为什么这个错误特别致命

文章的标题就是《C++17 之后》。读者照着敲一行就会撞上编译错误，而且撞的是全文最核心的"现代 C++ 改写了什么"那一段论证。

这类问题的代价不是"不够严谨"，是"读者从此不再信这个作者"。

## 根因

**这段代码从未被编译过。**

三篇正文的配套代码在同一个工程里逐步增长，但构建验证只覆盖了第 5 篇。第 1 篇和第 4 篇的代码写完即提交，把"目录里有文件"当成了"代码是对的"。

## 修法

不是把注释改对了事，而是**把论断变成编译器能检查的装置**：

```cpp
// 按值传入的函数参数——C++17 需要显式 move，C++20 起不需要
#if __cplusplus < 202002L
    return std::move(incoming);
#else
    return incoming;
#endif
```

两支都保留，由编译器选边；程序运行后打印 `__cplusplus`，读者能亲眼确认自己走的是哪一支。正文相应改成 C++17 / C++20 对照表。

事后验证：全量构建零 warning、`ctest` 2/2 通过、`probe_unique_ptr` 输出 `__cplusplus=201703` 自证走 C++17 分支。

## 沉淀

1. **数目对得上 ≠ 内容是对的。** 迁移、复制、重命名这类"看起来很机械"的操作，最容易漏掉真实构建这一步。
2. **凡涉及语言规则的论断，必须落成一个能被编译器检查的装置**，不能只写在正文里。已写入仓库根 `README.md` 的体例约定。
