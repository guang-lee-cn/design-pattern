# A04 · C 语言里的工厂（附：我偏爱哪几个 C 写法）

> 承接 C++ 主线：C++ 的工厂是用**类 / 虚函数 / 模板**搭出来的；C 里这些都没有，
> 但工厂照样存在——而且规模最大的那批系统（内核、驱动、插件框架）全靠它。
>
> 本节先把两边的机制逐条对齐，再给四档 C 版工厂的实测代码，最后是我的偏好清单（带理由和代价）。
> 代码：`code/A04_c/`；一条命令跑全部：`bash code/A04_c/build.sh`。

---

## 0. 一句话结论

**C 里没有"工厂模式"这个名词，只有三个原语**：

| 原语 | 用途 | 对应 C++ 的什么 |
|---|---|---|
| 结构体里放函数指针 | 多态 | 虚函数表 |
| 表驱动分派（`{key, handler}`） | 选择实现 | 注册表 / `std::map` |
| 链接器段 + `__start_/__stop_` | 自注册 | 静态初始化期注册 |

C 版工厂 = 用这三个原语手工搭出来的 C++ 版工厂。**代价从"设计"转移到了"纪律"**——
编译器帮你守的那些事（访问控制、穷尽性、析构、所有权），在 C 里全变成"人记得就行"。

## 1. 机制对齐表

| C++ 里的东西 | C 里的对应物 | 证据（实测） |
|---|---|---|
| `class` + 虚函数 | `struct` + 函数指针表 | `sizeof(struct sensor_ops) = 24`（名称 + 2 个函数指针） |
| 基类对象（含 vptr） | `{ const struct ops *ops; void *priv; }` | `sizeof(struct sensor) = 16` |
| 基类指针 | **不透明句柄** `struct sensor *`（头文件只给前向声明） | — |
| `new` 表达式 | `xxx_create()` 函数 | — |
| `virtual ~Base()` | 表里的 `destroy` 函数指针 | 靠命名与配对纪律，**编译器不管** |
| `std::function` 类型擦除 | **裸函数指针** | 表项 16 B vs C++ `std::function` 32 B（04b 实测） |
| 异常 | 返回 `NULL` / 错误码 | 调用方漏判 → 死机 |
| `protected` / `private` | **无**——只有不透明指针 + 头文件约定 | — |
| 静态初始化自注册 | ✅ 有，而且更彻底：链接器段 | 见 §4 |

一条值得记住的对照：**C 在这件事上反而更轻**。C++ 的注册表要 `std::function`（32 B，含小对象缓冲 + 两个内部函数指针），C 的注册表就是一个函数指针（表项 16 B）——**因为 C 根本不需要类型擦除**，它没有"异质可调用对象"这回事。

## 2. C 版四档（对应 C++ 三档 + C 独有一档）

代码：`code/A04_c/01_vtable_and_factory.c`（档 1、2）、`02_family_table.c`（档 3）、`03/04`（档 4）。

### 档 1：字符串分派 = 03 节的简单工厂

```c
static struct sensor *sensor_create_switch(const char *type)
{
    if (strcmp(type, "temp") == 0)     return temp_create();
    if (strcmp(type, "pressure") == 0) return press_create();
    return NULL;                      /* C 没有异常，错误只能靠返回值 */
}
```

和 C++ 版一模一样的三痛点，一模一样的三伤。**没有任何 C 特有的地方**——这档不用讲。

### 档 2：函数指针表 = 04a 节的注册表

```c
struct sensor_entry { const char *key; sensor_ctor ctor; };

static const struct sensor_entry registry[] = {
    { "temp",     temp_create  },
    { "pressure", press_create },
};
```

和 04a 的 `map<string, std::function<...>>` 是同一件事，但：

| | 04a（C++） | 档 2（C） |
|---|---|---|
| 表项的 value | `std::function<unique_ptr<T>()>`，32 B | 函数指针，**8 B** |
| 查找 | `map` 红黑树（O(log n)） | 线性数组（O(n)，n 是个位数） |
| 打错 key | 插进去一个空 `std::function`，调用时抛 `bad_function_call` | 返回 `NULL`，**不看返回值就段错误** |

**两个"失败模式"都很晚**，这是两种语言共同的坑，不是 C 独有的。

### 档 3：族表 = 05 节的抽象工厂 —— 这里出现第一个真正的差异

C++ 版（05 节）解决混搭靠"**选一个工厂对象**"；C 版靠"**只收一张表**"：

```c
struct platform_ops {
    const char *hw;
    struct uart *(*uart_create)(void);
    struct gpio *(*gpio_create)(void);
};

static void app_init(const struct platform_ops *plat)   /* 入口只收一张表 */
{
    uart_bind_gpio(plat->uart_create(), plat->gpio_create());
}
```

实测输出（`02_family_table.c`）：

```text
=== 反例：三个独立工厂函数，各自收平台名 ===
  [2] 混搭 A 的 uart + B 的 gpio（语法完全合法，编译器一声不吭）：
    uart 期望 gpio base = 0x40001000
    gpio 实际 base      = 0x50002000
    >> 平台不匹配：pinmux 写入错误寄存器组，UART 收不到数据

=== 正例：一族一张表，混搭无法表达 ===
  [3] app_init(&platform_a_ops)：  >> 匹配，pinmux 配置生效
  [4] app_init(&platform_b_ops)：  >> 匹配，pinmux 配置生效
```

**C 的族约束不在类型系统里，在参数形状里。** C++ 里写 `create_uart("A")` + `create_gpio("B")` 也是合法的——两边一样能犯错；区别在于**有没有一种写法让错误表达不出来**。C++ 用"工厂对象"提供它，C 用"一张表"提供它。功能上等价，表达手段不同。

## 3. 段自注册：机制与两条实测边界

### 3.1 机制（我们的最小复刻）

代码：`code/A04_c/sensor_registry.h` + `03_self_register_main.c` + `04_self_register_gyro.c`

```c
/* 把表项塞进自定义段；段名是合法 C 标识符，GNU ld 会自动生成 __start_/__stop_ */
#define REGISTER_DRIVER(key_, fn_)                                       \
    static const struct drv_entry                                        \
        __attribute__((used, section("sensor_registry"),                  \
                       aligned(sizeof(void *))))                         \
        reg_entry_##fn_ = { (key_), (fn_) }

extern const struct drv_entry __start_sensor_registry[];
extern const struct drv_entry __stop_sensor_registry[];
```

使用方只写一行 `REGISTER_DRIVER("gyro", gyro_read);`——**没有 central list，主程序不认识这个产品**。
对比 04a 的注册表：那版还需要有人显式调 `register_xxx()`（"装配点"），这版连装配点都不需要。

### 3.2 内核同款（本机头文件一手证据）

```text
include/linux/init.h:115    typedef int (*initcall_t)(void);              ← 表项就是函数指针
include/linux/init.h:272-274  static initcall_t __name __used
                                  __attribute__((__section__(__sec))) = fn;  ← 与我们完全同构
include/linux/init.h:286    #define __define_initcall(fn, id)  ... .initcall##id
include/linux/init.h:304-317 core_initcall(1) … device_initcall(6) … late_initcall(7)
```

**内核比我们多解决了一个问题，值得单独学**：段内顺序不可控 → 内核把**优先级编进段名**
（`.initcall0.init` … `.initcall7.init`、还有 `early` / `rootfs` / 同步变体 `1s`），
再在链接脚本里按名字顺序排列（`vmlinux.lds.h:903-918` 的 `INIT_CALLS_LEVEL(level)`，
每级用 `KEEP(*(.initcall##level##.init))`）。**顺序不由链接顺序决定，由段名决定。**

### 3.3 实测边界 1：静态库会吃掉你的注册项

同一个主程序，两种链接方式（`build.sh` 自动跑）：

```text
--- 链接方式 A：普通静态库链接 ---
=== 段自注册：段内登记项 2 个 ===           ← gyro 不见了
    pressure   -> 110
    temp       -> 250
    lookup("gyro")  =  -1

--- 链接方式 B：--whole-archive（强制拉入 .a 全部成员）---
=== 段自注册：段内登记项 3 个 ===           ← gyro 回来了
    pressure   -> 110
    temp       -> 250
    gyro       -> 700
    lookup("gyro")  = 700
```

**根因**：静态库成员的拉入条件是"它定义的符号被别人引用"，而自注册表项是 `static`（内部链接）——
**没有任何外部引用**，所以那个 `.o` 压根没进链接。段里自然没有它。

这条不是教科书上的理论，是**每个用段自注册的人都撞过的墙**：修法是 `--whole-archive`，或者用 `--undefined=` / 在别处真引用一下那个符号。内核不受影响是因为它是整体链接的 `vmlinux`，不存在"库成员被挑"的环节。

### 3.4 实测边界 2：段内顺序不是源码顺序

实测段内打印是 `pressure` 在前、`temp` 在后——与源码书写顺序相反。链接器只保证"同段聚集"，**不保证顺序**。
需要顺序时，只有两条路：把优先级编进段名（内核做法），或注册后自己排序。

### 3.5 另外三条已知限制（本轮未实测，按机制列出）

- `-Wl,--gc-sections` 可能把段丢掉（内核用 `KEEP()` 对冲）
- 段名必须是合法 C 标识符，否则 `__start_/__stop_` 不会生成
- `__stop_ - __start_` 是跨对象指针相减，严格按标准属于未定义行为；GCC/Clang 都容忍，但这是"约定俗成"而非"标准保证"

## 4. 我偏爱的四个 C 写法（带偏见）

### ① `struct` + 函数指针表 —— C 里唯一的多态表达

偏它的理由不是"像 C++"，而是相反：**它是显式数据，没有语言魔法**。
读一段 C++ 代码，你得知道虚调用、vtable、this 调整；读一段 C 代码，函数指针表就摆在那儿，
`sizeof` 能得到、`gdb` 能打出、能当参数传、能存进文件。

代价也很实在：`void *priv` 一上，**类型安全就交了**——传错 priv 编译器不管（C++ 里至少 `this` 是隐式的）。

### ② 不透明指针 + `create` / `destroy` 成对命名

C 里没有析构函数，所以"销毁"只能靠两件事：**命名成对**（`xxx_create` / `xxx_destroy`）+ **头文件只给前向声明**。

这是全篇最"纪律"的一条：**A03 节那个缺陷（工厂返回裸指针且无配对销毁入口）在 C 里不是"缺陷"，是常态**——
C 的世界里没人指望编译器守所有权，所以配对命名就成了合同。你看到 `create` 没看到 `destroy`，
在 C 项目里就应当直接判定为泄漏，而不是"再看看"。

### ③ 表驱动分派（`{key, handler}`）胜过 `switch`

同样的分派逻辑，两处写法：`switch` 是**代码**，表是**数据**。而这个差别很值钱：

| | `switch` / if 链 | 表 |
|---|---|---|
| 能打印吗 | 不能 | 能（调试、`--help` 自动生成） |
| 能遍历吗 | 不能 | 能（自检、遍历注册项） |
| 能表驱动生成吗 | 不能 | 能（代码生成 / 配置驱动） |
| 能单独测试吗 | 要构造整个函数 | 传一个 `const` 数组即可 |

代价：`switch` 有编译器的穷尽性提示（至少 `-Wswitch` 对枚举有效），表没有——
**运行时才知道 key 打错**。这笔账和 06 节的 `variant` 那三行结论是同一个道理。

### ④ 链接器段自注册 —— 我最喜欢，也最不敢随手用

喜欢它的理由：**它是唯一一个把"改动扩散"打到零的机制**。
新增一个驱动/插件 = 新增一个 `.c` 文件，主程序、构建列表、任何 switch 都不动。
这比工厂方法还彻底——工厂方法是"新类 = 新文件"，但**装配点仍然要改**（你得把新工厂对象传进去）；
段自注册连装配点都省了。这就是 §2 里说的"真正 OCP"。

不敢随手用的理由，就是 §3.3–§3.5 那三条：静态库吃掉、顺序不定、工具看不见。
**一句话：它买的是零改动，付的是可见性。** 现代团队里"grep 找不到注册点"是实实在在的成本——
新人接手时找不到 `main` 到实现的路径，代码审核也看不见谁注册了什么。

我的取舍：**框架级（内核 / 插件宿主）值得用，业务模块不值得**。

## 5. 我明确不偏爱的（唱个反调）

- **`void *` 到处传、连 ops 表都没有的"隐式约定"**——把多态退化成"调用方自己知道该传什么"，等于把编译期错误全部推到运行期
- **宏拼出来的伪类**（`#define CLASS(...)` / `#define METHOD(...)` 那一套）——制造一种语言里没有的抽象，读代码的人要先学会你的方言
- **只有一个实现的函数指针表**——06 节判据：没有变化就别买保险，这一条在 C 里同样成立，而且 C 里"保险"更贵（多了个间接层，少了编译器检查）
- **全局函数指针变量做"可替换钩子"**——隐式全局状态，测试之间互相污染。这和 04a 里 `RegistryA` 的病是同一个病，只是 C 版更隐蔽（没有构造函数，你连"它被改过"都看不见）

## 7. 对嵌入式 / 中间件项目的用处

- **rpc / 插件框架**：若将来要做"传输插件、协议插件"的自动登记，段自注册能省掉构建列表的挂载；
  但 Fast-DDS 这类工程是**静态库 + 共享库混装**，§3.3 那条墙一定会撞——要么 `--whole-archive`，
  要么老老实实保留显式注册表。**显式注册在库场景里更稳**，这也是它到现在还没被淘汰的原因。
- **反过来的启发**：C++ 里那些"自动注册"的库（如 A02 的 `llvm::Registry`）之所以还要求写一行宏，
  不是为了省事，而是**为了让注册点可 grep**。可见性与零改动之间，工业界普遍选了可见性。
