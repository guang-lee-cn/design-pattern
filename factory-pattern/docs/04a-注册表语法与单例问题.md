# 问题 1：注册表用到的语法逐个摊开

## 1.1 `using Creator = std::function<std::unique_ptr<Sensor>()>;`

**读法**：`Creator` 是一类"可调用物"的类型别名——**无参数，返回 `unique_ptr<Sensor>`**。

`std::function<返回类型(参数类型...)>` 是**类型擦除容器**，它把签名相同但类型不同的可调用物装成同一个类型：

| 能装什么 | 例子 |
|---|---|
| 普通函数 | `Sensor* make_temp();` |
| 函数指针 | `&make_temp` |
| 仿函数 | `struct Maker { Sensor* operator()(); };` |
| **lambda** | `[] { return std::make_unique<TempSensor>(); }` |
| 成员函数绑定 | `std::bind(&X::make, &x)` |

**两个语法易错点**：

- 模板参数写的是**函数类型** `void()`，不是函数指针类型 `void(*)()`。`std::function<void()>` 读作"可调用的东西"。
- `std::function` **可以为空**（默认构造出的就是空）。调用空 `std::function` 抛 `std::bad_function_call`——这正是 `map::operator[]` 能安全插入空槽位的原因（1.3 讲）。

**代价**：一次间接调用（内部函数指针/虚调用），比直接调 lambda 略慢。注册表方案的运行时开销就藏在这里。

## 1.2 `static std::map<std::string, Creator>& table()`

三个语法点：

**(a) 返回类型带 `&`** —— 返回引用而非拷贝。漏掉 `&` 每次调用会复制整张表，而且改不到原表。

**(b) 函数内 `static` 局部变量** —— 只在第一次执行到该行时构造，程序退出时销毁。C++11 起保证**线程安全的延迟初始化**：多线程同时首次进入，只有一个线程构造，其余等待。这与 Meyers Singleton（`static T& instance() { static T t; return t; }`）是同一机制。

**(c) 为什么把表放在函数里，而不是类的静态数据成员？**
- 类静态数据成员需要在某个 .cpp 里额外定义，且**初始化顺序跨翻译单元不确定**（静态初始化顺序问题）；
- 函数内 `static` 保证"第一次用到才建"，从根上规避这个陷阱；
- 写在头文件里也安全：类的成员函数默认 `inline`，标准保证 inline 函数的函数内静态局部变量**全程序共享一份**。

## 1.3 `table()[type] = std::move(creator);` 逐步骤

| 步骤 | 表达式 | 编译器实际做了什么 |
|---|---|---|
| 1 | `table()` | 返回 `std::map<std::string, Creator>&`（左值，可改） |
| 2 | `table()[type]` | 调 `map::operator[]`：**key 不存在就插入 `{type, Creator{}}`**，然后返回 value 的**引用** |
| 3 | `std::move(creator)` | **不移动任何东西**，只是 `static_cast<Creator&&>(creator)`，把参数当成右值看待 |
| 4 | `=` | 因为右边是右值，选中 **移动赋值** `operator=(Creator&&)`，把 lambda 的内部状态搬进槽位 |

**关于第 2 步的副作用（这是 `operator[]` 最坑的地方）**：`registry_annotated.cpp` 实测演示了：

```text
before: table size = 2
after : table size = 3  <-- 查表用 [] 的代价
```

只是"读一下" `table()["不存在的key"]`，表就被撑大了——顺手插入了一个**空的 Creator**，日后调它直接抛 `std::bad_function_call`，而且 `list()` 会把它列出来，自检逻辑看到幽灵条目。

> **规则：写用 `operator[]`，查用 `find()`。** `registry.cpp` 的 `create()` 用的就是 `find`。

**第 3 步为什么值得 move**：`std::function` 内部可能持有 lambda 捕获的状态，移动只搬指针，拷贝要复制内容（捕获对象不支持拷贝时甚至编译失败）。

**更直白的等价写法**（推荐在生产代码用）：

```cpp
tbl().insert_or_assign(type, std::move(creator));   // C++17：存在则覆盖，语义一眼明白
tbl().emplace(type, std::move(creator));            // 存在则保留旧的，不覆盖
tbl()[type] = std::move(creator);                   // 存在则覆盖（但有上面那个副作用）
```

**参数为什么按值传** `Creator creator`：调用方可以 `std::move` 进来，函数内再 move 进 map，全程零拷贝。若写成 `const Creator&` 就必然多一次拷贝。

## 1.4 `it->second()` —— 调的不是成员函数

`it->second` 是 `Creator&`（即 `std::function<...>&`），后面加 `()` 是**调用 `std::function::operator()`**，转发到真正装进去的 lambda。

参数不匹配会怎样？**编译期就报错**——`std::function` 只接受签名兼容的调用（返回类型可转换、参数可转换）。这是它比 C 风格 `void*` 强的地方。

## 1.5 lambda：装进表里的到底是什么

```cpp
register_sensor("temp", [] { return std::make_unique<TempSensor>(); });
//                      ↑ 捕获列表为空
```

- `[]` 捕获列表为空 → **无状态闭包**，可以隐式转换成普通函数指针
- 编译器为这个 lambda 生成一个**唯一的匿名类**，内含 `operator()`
- `std::function` 把该匿名类对象装进自己内部，此后靠统一签名调用，类型被"擦除"

**一句话理解注册表方案**：它把"工厂类层次"降级成"一堆 lambda 对象"。工厂方法要写 `class TempFactory {...}`，注册表只写一个 lambda，**类数量从 N 降到 0**。代价是：没有类型名字、调试器里看到的是一串 `lambda at registry.cpp:88`、无法在类上挂公共逻辑（比如统一的日志/校验）。

# 问题 2：它像单例，但没禁止构造/拷贝/赋值/移动——有问题吗

**有，分三层。先看事实。**

## 2.1 事实：编译器隐式生成了所有特殊成员函数

`registry_fixed.cpp` 用类型特征把这件事量化了（编译期事实，输出实测）：

```text
类型        默认构造  拷贝构造  移动构造
RegistryA   yes       yes       yes        ← 原始写法
RegistryB   no        no        no         ← 显式 delete
RegistryD   no        no        no         ← 私有构造 + Meyers 单例
```

**关键认知**：只要你不声明任何特殊成员函数，编译器就会替你生成默认构造、拷贝构造、拷贝赋值、移动构造、移动赋值、析构。**"全是静态成员"并不能阻止这件事。** `RegistryA a;` 和 `RegistryA b = a;` 都能编译通过——`sizeof(RegistryA) == 1`，你得到一个毫无意义的空对象。

## 2.2 三层问题

### 问题 ①：语义上允许了不该允许的操作

代码在表达"我只是一个函数集合"，但类型系统允许别人创建实例。这在 code review 里会制造噪音：读代码的人得自己去确认"这个类到底要不要实例化"。

**修法（成本最低）**：显式删除五个特殊成员函数，把设计意图从注释变成**编译错误**：

```cpp
class RegistryB {
public:
    RegistryB() = delete;
    RegistryB(const RegistryB&) = delete;
    RegistryB& operator=(const RegistryB&) = delete;
    RegistryB(RegistryB&&) = delete;
    RegistryB& operator=(RegistryB&&) = delete;
    ...
};
```

### 问题 ②：它不是单例，也不该假装是单例

单例的定义是"**保证只有一个实例**，并提供全局访问点"。`RegistryA` 的"唯一性"来自**没有任何实例、只有函数内静态变量**这一事实——这不是单例，是**纯静态工具类**。

两者区别很实际：

| | 纯静态类（A/B/C） | 单例（D） |
|---|---|---|
| 唯一性来源 | 没有实例可造 | 构造私有 + `instance()` |
| 能否替换/注入 | **不能**（静态函数写死在调用点） | 可以（`instance()` 是替换点） |
| 测试友好度 | 差（测试间互相污染） | 稍好（但仍需清理） |

**结论**：它没"忘了禁止"——它是**根本没打算做单例**，只是巧合地具备唯一性。而"没禁止"这件事确实该修（问题 ①），因为无害的宽松也是噪声。

### 问题 ③：全局状态的可测性（最贵的那个）

无论 A/B/C/D，注册表都是**进程级全局可变状态**。真实伤害在测试里：两个测试用例想注册不同的假传感器，会互相污染；测试顺序、并行执行都可能让结果漂移。

`registry_fixed.cpp` 里还有一处精确的细节：`RegistryD` 的 `is_move_constructible` 是 **no**——因为声明了拷贝构造/赋值（哪怕是 `= delete`）**会抑制移动构造的隐式生成**。这条规则常被忽略，写"禁拷贝"时若还想保留移动，必须显式 `= default` 移动构造。

## 2.3 四种修法取舍

| 方案 | 代码 | 适用 |
|---|---|---|
| **A 原始** | 全静态成员 | 只在"临时脚本级"代码里可接受 |
| **B `= delete`** | 显式禁止实例 | 想保留类语法（`Registry::make()`）时的最小修法 |
| **C namespace** | `namespace sensor_registry { ... }` | **本项目推荐**：全静态工具类的语言原生答案，天生不可构造/拷贝，无 `Registry::` 前缀噪音 |
| **D Meyers 单例** | 私有构造 + `instance()` | 需要"替换实例"作为测试缝（把表做成成员而非函数内静态） |

## 2.4 线程安全：比特殊成员函数更该关心的事

`table()` 的**初始化**是线程安全的（C++11 函数内静态保证），但 `std::map` 的**并发读写不是**。

两种务实做法：

1. **推荐（嵌入式惯用）**：约定"**注册只在启动期完成，运行期只读**"。main 初始化阶段把传感器全部登记完，此后只调 `create()`，无需任何锁。可以在 `create()` 里加个 `frozen_` 标志位，启动后调用 `register_*` 直接断言失败——把约定变成运行期检查。
2. **需要运行期动态注册**：加 `std::mutex` 保护插入，读路径用 `std::shared_mutex`（C++17）读并行。代价是一次锁开销，抵消掉注册表"调用开销小"的优势。

## 2.5 结论（两句话）

> **问题 1**：`std::function` 是类型擦除容器（装 lambda），`table()[type] = std::move(x)` 是"map 的 operator[] 插入并返回引用 + 移动赋值"，但 `operator[]` 有顺手插入空槽的副作用——**查表一律用 `find`**。
>
> **问题 2**：它不是单例，是纯静态工具类——唯一性来自"没有实例"，不是"禁止实例"。**修法优先选 namespace**；同时明确"注册只在启动期"的线程约定，比纠结特殊成员函数更值钱。
