## 一句话动机

第 3 节留下一个问题：简单工厂把 if-else 收敛到一处，但**这个函数体仍是高频改动热点**（判据 1 的三伤仍在）。工厂方法换了个思路——**不写分发函数，让"选哪个产品"变成"选哪个工厂对象"**。

## 结构对照

```cpp
// 简单工厂：一个函数 + if-else 分发
std::unique_ptr<Sensor> create_sensor(const std::string& type) {
    if (type == "temp")       return std::make_unique<TempSensor>();
    if (type == "pressure")   return std::make_unique<PressureSensor>();
    throw std::invalid_argument("unknown sensor type: " + type);
}

// 工厂方法：抽象工厂 + 每产品一个具体工厂
class SensorFactory {
public:
    virtual std::unique_ptr<Sensor> create() = 0;   // <-- 工厂方法本体
};
class TempFactory : public SensorFactory {
    std::unique_ptr<Sensor> create() override { return std::make_unique<TempSensor>(); }
};
class PressureFactory : public SensorFactory {
    std::unique_ptr<Sensor> create() override { return std::make_unique<PressureSensor>(); }
};
```

**决策搬迁了**：从"工厂函数体里的 if-else"搬到"装配点选哪个工厂对象"（`build_catalog()` / main）。工厂函数体不再需要修改——新增产品是新增类。

## 新增 `HumiditySensor` 的动作对照

| 动作 | 简单工厂 | 工厂方法 |
|---|---|---|
| 新增产品类 | 1 个 | 1 个 |
| 新增工厂 | — | **1 个**（类数量代价） |
| 改旧代码 | **改 `create_sensor()` 函数体** | 0 |
| 装配点登记 | — | push_back 一行（新代码，非改旧码） |
| 全量回归 | 需要（函数体被改） | **不需要**（旧文件字节未动） |

关键差别：简单工厂的"改函数体"必然触发伤 A（回归）、伤 B（仪式）、伤 C（冲突）；工厂方法的"加新类"三伤全免——新类是新文件，天然无冲突、不需要回归。

## 代价：类数量翻倍

**N 个产品 = N 个产品类 + N 个工厂类。** 这是工厂方法最实在的代价，在嵌入式项目里尤其刺眼（文件数、编译单元数、链接时间都在涨）。这也是为什么它只值当"工厂函数体确实是改动热点"时才上（第 2 节判据 1）。

## C++ 惯用变体：注册表（registry.cpp）

C++ 里有个更轻的写法能达到同样的 OCP 效果——**用 `map<key, 创建函数>` 替掉整个工厂类层次**：

```cpp
class SensorRegistry {
public:
    using Creator = std::function<std::unique_ptr<Sensor>()>;
    static void register_sensor(const std::string& type, Creator c) { table()[type] = std::move(c); }
    static std::unique_ptr<Sensor> create(const std::string& type) {
        auto it = table().find(type);
        if (it == table().end()) throw std::invalid_argument("unregistered: " + type);
        return it->second();
    }
private:
    static std::map<std::string, Creator>& table() { static std::map<std::string, Creator> t; return t; }
};

// 各模块自行登记（放在各自传感器的 .cpp 内，模块加载即完成登记）
SensorRegistry::register_sensor("temp", [] { return std::make_unique<TempSensor>(); });
```

### 三方案横向对照

| | 简单工厂 | 工厂方法 | 注册表 |
|---|---|---|---|
| 类数量 | 1 | 1 + N×2 | **1** |
| 新增产品改旧代码 | 改函数体 | 0 | 0 |
| **登记动作位置** | 工厂函数内 | 装配点 | **可分散到各产品 .cpp**（零合并冲突） |
| 未注册类型报错时机 | 运行期（throw） | **编译期**（抽象类不可实例化） | 运行期（throw） |
| 穷尽性检查 | 无 | 有（类层次清晰） | **无**（编译器不知道表里有几个） |
| 适合场景 | 产品稳定 | 产品少但频繁扩展 | 产品多、模块化、第三方插件 |

### 注册表的关键取舍（java9r 指出的）

注册表把"编译期穷尽性检查换成运行期灵活性"：
- **赢**：新增产品完全不碰工厂源码，且**多个模块可各自登记自己**（不同 .cpp 各写一行，git 层面天然无冲突）
- **输**：编译器不再知道合法 key 集合，打错 key 只在运行期炸；若合法类型实际是**封闭集合**，用工厂类层次 + `enum` 反而更安全

## 嵌入式选型建议

| 场景 | 选 |
|---|---|
| 产品集合封闭且已知（enum 可枚举），扩展少 | 简单工厂 / 工厂类层次（编译期安全） |
| 产品多、模块化、可能由第三方提供 | 注册表（.so 加载即登记） |
| 需要"一族配套产品" | 抽象工厂（第 5 节） |

## 一句话总结

> 工厂方法把"改函数体"换成"加新类"，买的是**零回归 + 零合并冲突**，付的是**类数量翻倍**。C++ 里注册表用 map 换到同样的 OCP，代价是丢掉编译期穷尽性检查。
