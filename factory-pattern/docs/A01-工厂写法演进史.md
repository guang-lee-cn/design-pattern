# A01 · 工厂写法的演进史：从「返回地址」到「返回所有权」

> 追加专题。补充 `01`～`06` 节未覆盖的**语言演进维度**：同一个工厂模式，在 C++98 和 C++11 之后是两种东西。

## 0. 先修正一下你的说法

你的观察基本对，但有一处需要精确化：

| 你的表述 | 修正后 |
|---|---|
| 智能指针出现前，返回值不带作用域和生命周期 | ✅ 对 |
| C++11 之后写法多样化，融合了智能指针技巧 | ✅ 对，但要说出**融合的是什么** |

**精确表述：**

- 旧工厂返回的是**地址**（`Product*`）——类型系统只承载"东西在哪"
- 新工厂返回的是**所有权 + 销毁策略**（`unique_ptr<Product, Deleter>`）——类型系统承载"谁负责、怎么销毁"

所以智能指针给工厂带来的**不是写法上的便利，是把所有权从注释里搬进了类型里**。

---

## 1. 前智能指针时代（C++98）：工厂只返回地址

代码：[`code/A01_evolution/01_before_smart_ptr.cpp`](../code/A01_evolution/01_before_smart_ptr.cpp)
编译：`g++ -std=c++98 -Wall`

实测输出（节选）：

```text
三个指针的静态类型完全一样：Product*
  a = 0x584e911a92c0   (heap)
  b = 0x584e911a92e0   (malloc)
  c = 0x584e911a9300   (pool)

--- 释放：三种产品三种销毁方式，逐个查表 ---
  a -> delete p
  b -> free(p)                 <-- 提示本身就是错的！
  c -> PoolSensor::release(p)  <-- 不是 delete！
```

三个指针的**静态类型完全相同**，销毁方式却**各不相同**：

| 产品 | 分配方式 | 正确销毁 |
|---|---|---|
| `HeapSensor` | `new` | `delete p` |
| `MallocSensor` | `malloc` + placement new | `p->~MallocSensor()` **再** `free(p)` |
| `PoolSensor` | 对象池 | `PoolSensor::release(p)` |

**类型系统对这个差异一无所知。** 写错任意一行，编译器一声不吭。

### 实测跑出来的意外：连「提示」本身都不完整

第一次跑的时候，我按提示写了 `std::free(b)`，结果 `[MallocSensor] 析构` **没有打印**——`free` 不调用析构函数。

也就是说，"记提示"这条路本身就不可靠：**提示里写的 `free(p)` 是错的，正确写法要先显式调析构**。人肉约定连一份准确的备忘都留不下来。

### 业界的三种应对（都是绕，不是解）

| 做法 | 代表 | 问题 |
|---|---|---|
| 文档 / 口头约定 | 绝大多数项目 | 实测已证明：连提示都写不全 |
| `std::auto_ptr` | C++98 标准设施 | 设计错误，见下节 |
| **绕开指针** | Qt `QObject` 父子树、COM `AddRef`/`Release`、工厂返回静态对象 | 把生命周期交给另一套机制（对象树 / 手工引用计数），工厂本身仍不表达所有权 |

## 2. `auto_ptr`：第一次尝试，方向对，设计错

代码：[`code/A01_evolution/02_auto_ptr_trap.cpp`](../code/A01_evolution/02_auto_ptr_trap.cpp)

### 版本边界实测（同一份代码，四种编译方式）

| 编译命令 | 结果 |
|---|---|
| `-std=c++98 -Wall` | 通过，**零警告**（它是 C++98 的正规设施） |
| `-std=c++11 -Wall` | 通过，`deprecated: use 'std::unique_ptr' instead` |
| `-std=c++17`（默认） | **仍然只是警告** ← 意外 |
| `-std=c++17 -D_GLIBCXX_USE_DEPRECATED=0` | `error: 'auto_ptr' is not a member of 'std'` |

**第 3 行是这节最值得记的事实：标准移除 ≠ 实现移除。** gcc 13 的 libstdc++ 在 C++17 下**仍然提供** `auto_ptr`（声明在 `unique_ptr.h:65`），只给 deprecated 警告。要看标准语义下的真正移除，必须显式关掉兼容层 `_GLIBCXX_USE_DEPRECATED`。

> 推论：**不能靠"编译器报不报错"判断某个设施是否还在标准里。**

### 运行结果：拷贝即掏空

```text
a.get() = 0x620183e012c0          ← 初始

执行 `auto_ptr<Product> b = a;` 之后：
a.get() = (nil)                   ← 被掏空
b.get() = 0x620183e012c0
```

`auto_ptr` 把「拷贝」和「转移所有权」**混成了同一个动作**。任何一次无意的值传递（传参、返回、放容器）都会把对象偷走，而**源码里看不出来**。

它还是**不能放进 STL 容器**（`vector<auto_ptr<T>>` 能编译，但 `push_back` 之后元素集体变空）。

**结论**：方向是对的（必须表达所有权），但选错了载体——用「拷贝」这个动作去表达「转移」。

## 3. C++11：分水岭——所有权进入类型

### 签名对比

```cpp
// C++98
Product* create(const char* kind);              // 返回地址

// C++11
std::unique_ptr<Product> create(const char* kind);   // 返回所有权
```

调用方不需要看文档就知道：**这个指针归我，出作用域自动销毁。**

### 关键新能力：自定义删除器（C++98 做不到）

```cpp
using FilePtr = std::unique_ptr<std::FILE, FileDeleter>;
```

实测输出：

```text
2. 自定义删除器 —— 返回类型自带销毁策略：
    [open_writable] fopen("/tmp/fp_a01_demo.txt")
    [FileDeleter] fclose(0x6176689da2e0)
    已经自动关掉了，调用方不需要知道「该用 fclose 还是 CloseHandle」
```

对比第 1 节的 `FILE*`：拿到 `FilePtr` 的人**不需要知道**该调 `fclose` 还是 `CloseHandle`——**销毁策略就写在返回类型里**。

这是 C++98 的工厂结构上无法提供的能力。硬件句柄场景（`fd`、`FILE*`、`mmap`、共享内存）尤其值钱。

### C++11 的遗憾：没有 `make_unique`

| 标准 | `std::make_unique<T>()` |
|---|---|
| **C++11** | 3 条 error — `'make_unique' is not a member of 'std'` |
| C++14 | 0 条 error |

`make_unique` **是 C++14 才补上的**，C++11 只有 `make_shared`。（C++11 里想用只能自己写三行。）

## 4. 智能指针解决的真正问题：所有权窗口

代码：[`code/A01_evolution/03_smart_ptr_factory.cpp`](../code/A01_evolution/03_smart_ptr_factory.cpp)

裸 `new` 到智能指针接管之间有一个窗口：

```cpp
Product* raw = new TempSensor(25.0);   // (1) 分配完成
//        ← 窗口：这里抛异常 / 提前 return，这块内存就没人接管
return std::unique_ptr<Product>(raw);  // (2) 所有权才被接管
```

用全局 `operator new` 计数器实证（不是"理论上会泄漏"）：

```text
3. 所有权窗口：
    捕获异常：构造中途失败
    未释放对象数：1 -> 2   （差 1 = 泄漏的那一个）
```

### 分配次数：`make_shared` 的收益也能量化

| 写法 | 分配次数 |
|---|---|
| `shared_ptr<T>(new T)` | **2** |
| `make_shared<T>()` | **1** |

`make_shared` 把**控制块和对象合并在同一块内存**。代价：对象析构后那块内存不能立刻还给系统（`weak_ptr` 存活期间）。

## 5. 「多样化」到底多在哪：两个正交维度

你感觉到的「写法很杂」，本质是**两个独立维度的组合**：

|  | **类型在编译期确定** | **类型在运行期确定** |
|---|---|---|
| **不需要多态** | 模板工厂（C++11/14）<br>`make_unique<T>(args...)` | — 少见 |
| **需要多态** | — 少见 | 类层次工厂（GoF 原版）<br>lambda 注册表（C++11） |

再加一条独立维度：**值语义 vs 指针语义**

- `variant<T...>` + `std::visit` → 封闭集合，**零堆分配**（C++17）

实测输出（[`04_modern_forms.cpp`](../code/A01_evolution/04_modern_forms.cpp)）：

```text
1. 模板工厂     : TempSensor -> 250      (编译期定类型，无虚工厂类)
2. 类层次工厂   : TempSensor -> 250      (运行期多态，GoF 原版)
3. lambda 注册表: PressureSensor -> 110  (运行期定类型，可分散登记)
4. variant      : 110   (sizeof=16，无 new、无虚表)
```

### 为什么 C++11 之后突然多出好几种写法

因为 C++11 一次给了三个工具，**工厂的实现方式被这三个工具重写了**：

| 新工具 | 它让工厂变成了什么样 |
|---|---|
| **移动语义**（`unique_ptr` 可拷贝性→可移动） | 工厂终于能"返回"所有权而不靠掏空把戏 |
| **lambda** | 工厂类层次可以降级成一堆匿名函数（注册表形态） |
| **可变参数模板 + 完美转发** | 一个模板函数顶掉 N 个工厂类（`make_unique` 形态） |

前智能指针时代，工厂只有一种写法：**写一个返回裸指针的函数，然后在文档里写清楚该怎么删。**

## 6. 时间线

| 时间 | 事件 | 对工厂的影响 |
|---|---|---|
| C++98 (1998) | `auto_ptr`、无移动语义 | 所有权只能靠文档 |
| 2001 | Boost.SmartPtr | 引用计数进入库层面 |
| **C++11 (2011)** | `unique_ptr`/`shared_ptr`、移动语义、lambda、变参模板 | **所有权进入类型系统**；工厂写法开始分叉 |
| C++14 (2014) | `make_unique` | 补上 C++11 的缺口 |
| C++17 (2017) | `variant`、`if constexpr`、CTAD | 值语义工厂登场（无堆、无虚表） |
| C++20 (2020) | concepts | 工厂的约束可写成可读的概念 |

---

## 7. 一句话总结

> **旧工厂返回「东西在哪」，新工厂返回「这是你的，而且该怎么处理它」。**
>
> `auto_ptr` 想在 C++98 就做这件事，但选错了载体（用拷贝表达转移）；
> `unique_ptr` 靠 C++11 的移动语义才第一次做对；
> 加上变参模板和 lambda 之后，工厂从"一种写法"变成了"四象限里的四种写法"。
