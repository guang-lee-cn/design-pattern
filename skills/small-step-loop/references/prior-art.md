# 先例扫描与可用性拆解（2026-09-20）

> 目的：在自建"小步迭代 + 间奏可停 + 断点快启"协同协议之前，先确认市场上有没有能直接用的东西。
> 方法：GitHub / 社区 / 官方文档三类来源，逐个拆"它解决什么 / 我们要什么 / 差距在哪"。

## 0. 先把问题拆准

李广的原话拆成三个**可独立验证的失效模式**：

| # | 失效模式 | 症状 | 根因 |
|---|---|---|---|
| F1 | **超限输出** | "一次性不能输出太多内容" | 单步产出无**结构边界**；agent 以"把事做完"为目标，不以"可被审阅"为目标 |
| F2 | **无自然停点** | "审核的时候太累，无法停下来" | 停点在 agent 的默认行为里是缺失的；现有框架都假设 agent 该连续跑到任务完成 |
| F3 | **断链** | "中途中断会导致下次接续的时候思维断链" | 状态只活在会话里，没固化到磁盘；恢复靠重建而非读取 |

**关键判断**：F1/F2 的稀缺资源是**人的审阅带宽**（李广的注意力），F3 的稀缺资源是**agent 的上下文**。
市面上几乎所有框架都在解 F3（agent 会忘），**没有一个把"审阅带宽"当一等公民**。
这就是自建的理由——不是重复造轮子，是补一个没人管的约束。

## 1. 规格驱动开发（SDD）三件套

| 项目 | 星标 | 结构 | 它解的 | 对我们的差距 |
|---|---|---|---|---|
| **GitHub Spec Kit** | ~71k | 4 阶段 `/speckit.specify → plan → tasks → implement`；YAML 定义工作流，**支持 pause / resume**；每 spec 一个 git 分支 | 把模糊 prompt 变可执行任务；规范文件随代码提交 | ⭐ **最值得借的是"每 spec 一分支 + 规范随代码提交"**。但阶段粒度太粗（一个 spec 的产出仍是一整块），且它的 pause/resume 是**工作流节点**级的，不是**审阅预算**级的。社区反馈：token 消耗高、流程慢 |
| **BMAD-METHOD** | ~2.8k | Analysis → Planning → Solutioning → Implementation；21 个角色 agent；v6 已迁到 `.claude/skills` | 用角色分工覆盖完整交付链 | 面向团队与长周期产品；学习曲线陡。**21 个 agent 角色对"一个人 + 一个 AI"是负资产** |
| **claude-code-spec-workflow** (Pimzino) | ~2.5k | feature 流（需求→设计→任务→实现）+ bugfix 流（报告→分析→修复→验证） | 轻量、单命令安装 | "双流程（新功能 / 修 bug）"这个切分值得抄；但同样没有单次产出上限 |
| **OpenSpec** | — | 草稿提案 → 实施 → 验证 → 归档；`openspec/changes/` 物理隔离 | 轻量迭代、快速补丁 | ⭐ **`changes/` 独立目录隔离**值得抄（避免未定稿内容污染主树）。仍缺产出预算 |

**结论**：这四条都是**阶段框架**，解决"顺序别乱、产物别丢"。它们**不解决"单次太大"**——因为它们的用户是有 review 文化的团队，量大就开 PR 让人慢慢看。我们没有那个人力。

## 2. 交接与断点续传（最接近我们的一条线）

| 来源 | 机制 | 可借的部分 |
|---|---|---|
| **Harness Engineering** (strangelove-ai) | `PROGRESS.md` 作为"continuity artifact"；在 `AGENTS.md`/`CLAUDE.md` 里写死 **clock-in / clock-out 例程**；把 "更新 PROGRESS.md" 写进 Definition of Done | ⭐⭐ **五要素**：当前状态 / 已完成+**验证记录** / 当前阻塞 / 下一步动作 / **仓库与运行时快照（git hash + 测试通过率）**。他们实测把新会话重建成本从 15 分钟压到 3 分钟 |
| **state-management-across-sessions** (skilldb) | 把 git 提交当作 **state journal**；每个有意义的工作单元后提交；**会话结束不允许有未提交改动**，至少一个 **WIP commit**；提交信息要说明**任务状态**而非仅"改了什么" | ⭐⭐⭐ 与李广的第 3 条要求（一迭代一提交）**天然重合**。`wip:` 前缀 + "不推不提交就是看不见"直接采纳 |
| **workflow-checkpoint** (OpenClaw skill) | `PLAN → EXECUTE → VERIFY → CHECKPOINT → RECOVER`；JSON checkpoint；恢复时**校验产物仍存在** | ⭐ 六态 + **恢复时校验产物**（不是只读状态） |
| **memory-management** (easyplatform) | checkpoint 文件必须含 **Recovery Instructions**（"该读哪个文件、从哪一行继续"）；每 20–30 次操作更新一次 | ⭐ "恢复指令要能照着做"——我们的恢复协议必须给出**可直接执行的动作**，不是描述 |
| **Manual for AI Development Collaboration** (jaydenhwk) | `[ANALYZE] [IMPLEMENT] [REVIEW] [DEBUG] [REFACTOR] [DOCUMENT] [CONTINUE]` 命令前缀；project manifest 模板；会话启停模板 | ⭐ 命令前缀让"我现在要你做哪一类事"零歧义。**会话启停模板**正是我们要的间奏 |

**结论**：这条线把 F3 解得很好，但**完全不管 F1/F2**——它们默认"人类会一直跟着看"。

## 3. 审阅带宽（唯一正面打 F1/F2 的一条线，且都是博客非工具）

| 来源 | 机制 | 可借 |
|---|---|---|
| **"Ship Small Chunks"** (fazm.ai) | 一条可执行的判据：**"如果你不能在 15 分钟内 review 完这个 PR，任务就太大了，拆"**。每个 chunk 一份独立 spec，独立 agent 会话，按依赖顺序合并 | ⭐⭐⭐ **把"太大"变成可判定**。v1 曾把这条量化成数字预算表，v2 已改用**结构边界**（理由见 §7） |
| **"Coding Agents Create Decision Fatigue"** (cyberdevtech) | ① **看开场叙述分诊，不要先读代码**；② 三档 **Accept / Question / Reject**；③ Question 档**一次只问一个问题**，问完就等；④ **一个 review block 最多 5 个输出，然后硬停**；⑤ 说不出"这一步的架构意义一句话"就降级到 Question | ⭐⭐⭐ **直接对上"审核太累无法停"**。"预设上限，在还没麻木的时候就停"这条纪律是关键 |
| **"How to talk with AI"** (worldprogramming) | **micro-blueprint**：AI 先给"一个失败测试 / 五行类型定义"这种**微契约**，人只审这一小块，锁定意图后再实现；自动反馈（编译/类型/lint/测试）走确定性通道，人只审**领域意图与架构** | ⭐⭐⭐ "先出微契约再实现"是**把审阅成本压到最小的机制**，比"先实现再切碎"更好 |
| **AI Code Review Bottleneck** (volanea) | 按 **可逆性 / 影响面** 给变更分级定审阅强度；**机械改动与行为改动必须分离提交**；要求意图优先的 PR 描述（Problem/Approach/Behavioral proof/Non-goals/Risk） | ⭐ **"机械改动与行为改动分离"**——我们做批量文档编辑时正中此坑（一次改了 11 处标注） |
| **guvi: Best Practices for Coding with AI Agents** | **定义 stopping conditions**——未预期的错误 / 需业务判断的决策点 / 完成一个应被审的单元 / 动到范围外文件，任一命中即停并交人 | ⭐ 我们的"硬停条件"直接由此细化 |

**结论**：F1/F2 的解法**只存在于工程博客与个人经验**，没有被固化成可加载的技能。这是我们的空位。

## 5. 拆解结果：我们要建什么

综合下来，**没有一个现成方案可以直接用**；但**每一个都有一块可拆的零件**。最终方案 = 五个零件的重新组合：

| 零件 | 来源 | 我们怎么改 |
|---|---|---|
| 交接文件五要素 | PROGRESS.md（Harness Engineering） | 加上 **`next` 必须唯一**、**`head` 必须与 git 对齐**，并做成可机械校验（`check_state.py`） |
| git 作为状态日志 | state-management-across-sessions | 强化为**用户明确要求的"一迭代一提交"**，并把 `verify` 命令写进提交信息 |
| 可判定的"太大" | Ship Small Chunks（15 分钟判据） | 降级为**自检信号**（§2.4 四问），不作为数字门禁——理由见 §7 |
| 审阅分诊 + 硬停 | Decision Fatigue 协议 | 固化成给李广的**操作卡**（看开场卡 → 三档 → 5 个输出硬停） |
| 微契约先行 | How to talk with AI | 变成迭代单元的**入场条件**：先给验证命令与变更清单，确认后再动 |
| 门禁四态 / 降级记账 / 反合理化 | `iso/`（自有） | 直接继承，仅把粒度从"阶段"改到"步" |

**与所有先例的根本差异**：我们把**人的审阅带宽**设为一等约束，把**"能安全停下"**当作交付物的属性来验收，
而不是把"跑完了"当完成。这是先例里没有的。

## 6. 附带发现（记录以免重复踩）

- `~/code/skills/agent-skills/` 目录名带前缀，但**技能目录内是 `skills/<name>` 结构**，不在根目录——
  用 `ls skills/` 而不是 `ls`，`cat skills/<n>/SKILL.md` 而不是 `cat <n>/SKILL.md`。
- WSL 里 `for f in a b c; do ...; done` 的循环变量**会被外层 shim 吃掉**（实测：5 个文件全部 `cat ''` 失败）。
  逐条写绝对路径，或在 Python 里循环。

## 7. v2 修订记录：为什么删掉了预算表（2026-09-20）

**触发**：李广在 v1 交付后直接指出——

> "这个规定很死板，会导致模型为了满足硬要求降低输出质量。我们在内容规划上合理划分好章节，
> 按照章节里面的节迭代即可，不去卡死内容长度、代码长度等。"

**v1 错在哪**：

v1 用七个数字上限（文件 ≤3 / diff ≤200 行 / 正文 ≤80 行 / 图 ≤1 …）来保护审阅带宽。
这犯的是 **Goodhart 定律**的标准错误——**当一个指标成为目标，它就不再是好指标**：

- 数字上限**可被合规**，于是最省力的路径是向它妥协：删掉必要的代码示例、
  把论证压成结论、把本该写完的一节截成两轮；
- 结果是产出**符合预算但没有价值**，而且**更难审**——因为读者要额外判断"这里是不是被砍过"；
- 更隐蔽的代价：它把"拆步"变成了**凑数字**的行为，而不是**找结构接缝**的行为。

而真正的审阅成本是**需要同时建立几个心智模型**，这个量由结构决定，与行数相关性很弱：
300 行的强内聚重构可能 3 分钟看完；两个各 40 行的无关改动却要切换两次上下文。

**v2 改法**：

| 维度 | v1 | v2 |
|---|---|---|
| 边界依据 | 数量（文件数 / 行数） | **结构**（章 → 节；一节 = 一单元） |
| 拆步判据 | 超限即拆 | **§2.4 四问**（质性自检，不设阈值） |
| 保留的量化项 | 七项 | **两项**：每轮推进 1 个单元、每轮提问 ≤1（都是交互带宽，不是内容质量） |
| "太大"的判据 | 15 分钟折算成行数 | 降级为**自检信号**，不作风禁 |
| 新增防线 | — | **反 Goodhart 条款**："拆分的理由必须是结构上独立，不能是数字上超了" |

**保留下来的核心洞察**（这部分 v1 是对的）：
审阅带宽确实是稀缺资源，且确实需要被机制保护——只是**保护手段不该是数字，应该是结构**。
一条内聚的节，作者自己就愿意多审；一堆被截断的碎块，谁也审不出东西。
