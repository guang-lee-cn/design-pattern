# 小步迭代协同协议

## 0. 一句话模型

> **稀缺资源不是 agent 的上下文窗口，是李广的审阅带宽。**
> 本协议的全部设计都在保护后者：**单步产出一节、结构自足 → 到点就停 → 停前落盘 → 恢复只读一个文件。**

三个失效模式与三条对策（诊断依据见 `references/prior-art.md`）：

| 失效 | 症状 | 对策 |
|---|---|---|
| **超限输出** | "一次性不能输出太多，审核太累" | **单元边界**（按内容结构切到"节"，见 §2）；**不以行数卡量** |
| **无自然停点** | "无法停下来" | **停机协议**：单元完成即停，不等指令；停前走落盘例程 |
| **断链** | "中断后下次接续思维断链" | **STATE.md + 一迭代一提交**：恢复 = 读一个文件 + 对齐 git |

**与 `iso` 技能的分工**（避免撞车）：`iso` 管**阶段**（想清楚→设计→实现→集成，门禁是 Y/N）；
本技能管**步子**（阶段内部怎么切、怎么停、怎么续）。两者可叠加使用，不互相依赖。

## 1. 迭代单元契约

一个"步"必须**同时**满足五条，缺一即应拆成两步：

| # | 条件 | 判据 |
|---|---|---|
| 1 | **单一意图** | 能用一句话说清"这一步让 X 从 A 变成 B"，句中不含"顺便" |
| 2 | **结构自足** | 命中 §2 的切分依据；读者/调用方跳过本单元，不影响其他部分 |
| 3 | **可机械验证** | 存在一条命令，跑完能判通过/不通过。**不接受"目测还行"** |
| 4 | **可独立提交** | 能单独 commit，且该 commit 上仓库处于可工作状态 |
| 5 | **无跨步悬空** | 不留"半成品引用尚不存在的接口"；必须留时标 `TODO(next-step)` 并登记到 STATE.md 的阻塞项 |

**入场纪律（微契约先行）**：动手前先给李广三行——变更清单（哪几个文件）、验证命令（跑什么）、非目标（这步不做什么）。
他确认后再写。**先给契约的成本远低于先给产出的成本**。

## 2. 单元边界（由内容结构决定，不由行数决定）

### 2.1 为什么不用数字上限

v1 曾规定"变更文件 ≤3 / diff ≤200 行 / 正文 ≤80 行"。**该表已废止。** 原因不是它太严，是它**错**：

数字上限是可以被"合规"的，于是模型向它妥协——删掉必要的代码示例、把论证压成结论、
把本该写完的一节截成两轮。产出变成**符合预算但没有价值**。
这是 Goodhart 定律的标准失效：**指标一旦成为目标，就不再是好指标。**

真正决定审阅成本的不是"多少行"，是**李广需要同时建立几个心智模型**。这个量由结构决定，
与篇幅相关性很弱：一段 300 行的强内聚重构可能 3 分钟看完；两个各 40 行的无关改动却要切换两次上下文。

> **所以边界从"数量"改为"结构"。宁可一步写 400 行内聚的内容，也不要两步各 40 行的碎屑。**

### 2.2 切分依据（按优先级）

| 优先级 | 依据 | 判据 |
|---|---|---|
| 1 | **内容结构** | 长文档 = 章 → 节。**一个节 = 一个单元**。节没写完就不停 |
| 2 | **可验证边界** | 存在一条命令能判定"本单元完成"。找不到 → 说明节的定义还不清楚，先定节 |
| 3 | **可独立提交** | 单独 commit 后，仓库仍处于可工作状态（代码能编译 / 文档内部无断链 / 无悬空引用） |

### 2.3 什么叫"一个节"（可操作定义）

四个条件全中才算一节：

1. **有独立标题**——文档里是一个 `##`；代码里是一个模块 / 类 / 接口
2. **结论自足**——能一句话说清"本单元让读者或系统从 A 得到 B"
3. **可跳过**——略过它，其他节依然读得懂。**这是最硬的判据**
4. **不含"顺便"**——没有为了凑齐本节而塞进来的东西

**推论**：一节的篇幅由它的论证需要决定。一节要 400 行代码就写 400 行；一节只需 30 行就写 30 行。
**不因"超了"而拆，不因"少了"而凑。**

### 2.4 什么时候该拆（质性自检，不设阈值）

停机前问四问，**任一为"是"，本单元其实是两个**：

- [ ] 这一轮里有**两个互不依赖**的改动吗？（能分别回退吗？）
- [ ] 开场卡里需要解释**超过三条**因果关系吗？
- [ ] 李广需要核实**超过一个**承重假设吗？
- [ ] 有哪块内容是"为了这轮看起来完整"才塞进来的吗？

**关键区分**：拆分的理由必须是"**结构上独立**"，不能是"**数字上超了**"。
若是后者，你在制造假合规——把一节劈成两轮，读者反而更难判断进度。

### 2.5 保留的量化纪律（只有两条）

| 维度 | 值 | 为什么它不受 Goodhart 影响 |
|---|---|---|
| 每轮推进的单元数 | **1** | 这是交互带宽，不是内容质量；多推一个单元不会让任何一个更好 |
| 每轮向李广提问数 | **≤ 1** | 同上。多个问题 → 分多轮，别让他一次持有多个决策 |

### 2.6 明确不受限的项（v1 曾限，现全部解除）

变更文件数 · diff 行数 · 新建文件数 · 正文回复行数 · Mermaid 图数 · 代码块数 · 小节字数。

**唯一保留的分离原则**：纯机械改动（批量替换、全量重命名）**必须单独成一步**，不与行为改动混在同一提交。
但这与规模无关——是为了让 `git diff` 保持"可读 = 可回退"。

## 3. 停机协议

### 3.1 三种停机，语义不同

| 类型 | 触发 | 停前必做 |
|---|---|---|
| **间奏停**（正常） | 一个迭代单元完成 | ① 跑验证命令 ② 公示改动清单 ③ commit ④ 更新 STATE.md ⑤ 报一条下一步 |
| **硬停** | 命中 §3.2 任一条件 | 同上，另加：第 ④ 步标注未完成原因，第 ⑤ 步给出重入方式 |
| **异常停** | 被打断 / 上下文将满 / 用户叫停 | **先落盘再解释**：`wip:` 提交 或 完整提交；STATE.md `status: interrupted`，写清"手上做到哪、下一句该说什么" |

### 3.2 硬停条件（命中任一，立即停，不许"再往前走一点"）

1. 发现**本单元其实是两个结构单元**（§2.4 四问任一为是）——立即停，把第二个登记为下一单元
2. 遇到需要李广拍板的新决策点
3. 发现上游假设被推翻（对应 iso 的回滚触发）
4. 验证失败且根因未定位（**不许"先往下走，回头再修"**）
5. 需要动到范围外的文件
6. 需要外部动作（推送 / 发布 / 发邮件）
7. 待拍板问题已达 1 个仍未答复

### 3.3 停机铁律

1. **无悬空态**：任何时刻停下，仓库都不允许处于"别人看不出发生了什么"的状态。至少一个 WIP 提交。
2. **单一下一动作**：STATE.md 的 `next` 永远只有一条，且是**可直接执行**的动作。
   ✅ `跑 python scripts/check_mermaid.py posts/02-*.md 并把结果贴回来`
   ❌ `继续推进第 2 篇`
3. **不替用户回答**：门禁未通过就是未通过。可以给建议，不能替他确认。
4. **恢复会话不产出**：恢复阶段只做对齐与确认，不动手实现。

## 4. 状态文件 `STATE.md`

**固定路径：项目根 `STATE.md`**（一个项目只允许一个，不设第二处）。

### 4.1 结构

```markdown
---
project: design-pattern
updated: 2026-09-20T10:12:00+08:00
phase: P1 工厂模式 Blog
step_id: S-014
status: done
head: a1b2c3d feat(posts): 第2篇骨架与图
verify: python scripts/check_mermaid.py posts/02-*.md
---

## 已完成（含验证证据）
- [S-013] 迁移目录到 WSL 并初始化 git —— `git log --oneline` → 12 个提交，工作树干净

## 下一步（唯一）
- 动作：写第 2 篇的"三种工厂不是并列模式"小节，先出变更清单待确认
- 触发词：`继续`

## 阻塞
- none

## 决策
- D-004 文档交付以 markdown 为准，可视化走内嵌 mermaid（李广 2026-09-16）

## 待拍板（≤1）
- none
```

### 4.2 字段为什么必须（缺一即视为断链）

| 字段 | 作用 |
|---|---|
| `updated` | 判断信息新鲜度 |
| `step_id` / `phase` | 定位 |
| `status` | `pending` / `active` / `done` / `interrupted` |
| `head` | **把磁盘现实与文字描述锚在一起**——恢复时用它和 `git log` 比对。记录的是**本步工作提交**的短 hash，不含随后的 `chore(state):` 提交 |
| `verify` | 恢复时**重跑一次**，证明 `done` 不是自称的 |
| `下一步（唯一）` | 恢复后的第一件事 |
| `阻塞` | 没有就写 `none`，不留空 |
| `决策` | 防重复讨论已定型的事 |
| `待拍板` | 承接 §6 审阅分诊的问题 |

### 4.3 状态机（两个层级，别混）

| 层级 | 位置 | 取值 | 含义 |
|---|---|---|---|
| **当前步状态** | `STATE.md` 的 `status` | `pending` / `active` / `done` / `interrupted` | 描述"此刻手上这一步" |
| **单元状态** | `ITERATION_PLAN.md` 表格的 `状态` 列 | `pending` / `active` / `done` | 描述队列里每个单元 |

`interrupted` 是**会话级标记**，只出现在 `STATE.md`：表示上次是被打断的。
此时该单元在 `ITERATION_PLAN.md` 里退回 `pending`，中断点写进 `STATE.md` 的阻塞项。

**硬规则：单元在 `ITERATION_PLAN.md` 里不允许长期停在 `active`。**
会话结束时，它必须变成 `done`（已提交），或退回 `pending`（未完成）并写明断点在哪。

## 5. 恢复协议

**入口：李广说 `恢复 <项目名>`（或"接着上次的做"）。**

AI 侧动作顺序固定，不得跳：

```bash
# 1) 读状态（唯一必读文件）
cat STATE.md
# 2) 对齐 git 与 STATE.md 的 head
git log -3 --format='%h %s' && git status --short
# 3) 重跑 STATE.md 里的 verify 命令
```

4. 输出**恢复卡**（≤10 行）：
   ```
   【恢复】design-pattern / P1 工厂模式 Blog / 上一单元 S-013 done
   git  : a1b2c3d 与 STATE.md 一致，工作树干净
   验证 : check_mermaid.py → 7/7 OK
   下一步：<STATE.md 的 next 原文>
   待拍板：none
   要我开始吗？(Y/N)
   ```
5. 等 `Y`。**恢复阶段不写代码、不产出内容。**

**对齐失败三种情形，动作不同（不许自行脑补）**：

| 现象 | 含义 | 动作 |
|---|---|---|
| `head` 既不是 tip，也不是 `chore(state):` 提交的父提交 | 有未记录的工作 | 先查 `git log` / `git status`，把差异报给李广，等指示 |
| `verify` 命令失败 | `done` 是假的 | 该单元退回 `pending`，贴出失败输出，说明是重跑还是改 |
| `STATE.md` 不存在 | 从未初始化 | 走 §7 项目初始化，**不直接开工** |

**恢复成本预算：≤ 2 分钟、≤ 3 条命令、0 次猜测。** 超出说明上一步的落盘没做够。

## 6. 审阅分诊（给李广的操作卡）

1. **只看开场卡**（变更清单 + 验证证据 + 下一步），先分诊，**别先读代码**。
2. 三档：

   | 档 | 触发 | 动作 |
   |---|---|---|
   | **收下** | 验证证据齐、决策与意图一致、无可疑假设 | 抽检 → 继续。约 2 分钟 |
   | **一问** | 有一处承重假设你无法核实，或否决了你本会选的方案 | 写**一个**问题，等答复，**此时先别读代码** |
   | **打回** | 开场卡说不清"这一步的架构意义"、改动跨了两个以上结构单元、有多个未核实的关键假设 | 一句话说为什么，要求重切。不展开长理由 |

3. **硬停**：连续审到第 5 个输出就停，离开十分钟。上限在开始前设好，不是在麻木时才发现。
4. 说不出"这一步的架构意义一句话" → 降级到 **一问**。

## 7. 项目初始化（一次性）

新项目接入本协议时，产出三件（模板见 `assets/`）：

| 文件 | 作用 |
|---|---|
| `STATE.md` | 断点续传唯一入口 |
| `ITERATION_PLAN.md` | 迭代队列：每行一个可提交单元（id / 意图 / 验证命令 / 依赖 / 状态） |
| `DECISIONS.md` | 已定型决策 + 理由，防重复讨论 |

```bash
git init && git add -A && git commit -m "chore: 接入 small-step-loop 协议（STATE/ITERATION_PLAN/DECISIONS）"
```

初始化本身算**一个迭代单元**，也要走 §3 停机协议。

**初始化的 `verify` 不能只数文件数。** 一次真实构建（或一次端到端运行）才算有效验证：

> 2026-09-20 首次实战：迁移 54 个文件、源目录与目标目录逐项对账**全部相等**，
> 但补跑一次 `cmake --build` 立刻报出一个**从未被编译过**的源文件里的知识性错误
> （把 C++20 才生效的规则当成 C++11 起就有，`return incoming;` 匹配到已删除的拷贝构造）。
> **数目对得上 ≠ 内容是对的。** 迁移、复制、重命名这类"看起来很机械"的单元尤其容易漏这一步。

## 8. git 协议

- **一迭代一提交**。提交粒度 = 迭代单元 = 一个回退点。
- **状态提交单独标记**（协议里唯一允许的"第二个提交"）：
  `head` 在物理上不可能恒等于 `git log -1`——因为 STATE.md 自己也要提交，提交后 HEAD 必然前移。
  约定：**同步 STATE.md 的那次提交用 `chore(state):` 前缀**，紧随工作提交之后，每步至多一次。
  于是每步最多两个提交：`<工作提交>` + `chore(state): <step_id> 定格`。校验脚本按此判定。
- **提交前公示**：先列改动清单（文件 + 变更摘要），李广确认后再提交。
- 提交前必跑：该单元的 `verify` 命令 + `git status` 确认无意外文件。
- 提交信息格式：
  ```
  <type>(<scope>): <subject>

  step: <step_id>
  verify: <验证命令>
  ```
  `type` ∈ `feat|fix|docs|refactor|test|chore|wip`
- **会话结束不允许有未提交改动**。确需留半成品 → `wip:` 提交，并在 STATE.md 标 `interrupted`。
- **推送是对外动作**，每次单独确认，不自动执行。
- **机械改动与行为改动分离提交**（批量替换与逻辑修改不能混在一个 commit）。

## 9. 校验与自检

### 9.1 脚本校验（停机前跑）

```bash
python "<skill>/scripts/check_state.py" <项目根>
python "<skill>/scripts/check_state.py" <项目根> --resume    # 只打印恢复卡
```

校验项：front block 七个必需字段齐全、`status` 取值合法、
`head` 与 git 提交对齐（接受 §8 的 `chore(state):` 两段式）、`verify` 非空、
`下一步（唯一）` 恰好一条、`待拍板 ≤1`、工作树无未提交改动。
输出 `[!!]` 为必须修，`[!]` 为警告。退出码 1 表示存在 `[!!]`。

### 9.2 人工自检（每次停机前）

- [ ] 命中 §2.3「一个节」四条件？（独立标题 / 结论自足 / 可跳过 / 无"顺便"）
- [ ] 过 §2.4 四问，无一项为"是"？
- [ ] 有验证命令，且**已执行**、结果**已记录**？
- [ ] 该命令是**实质性**检查（一次能失败的构建 / 运行 / 断言），而不是"文件数对得上"这类形式指标？
- [ ] 已 commit（或 `wip:` 提交），工作树干净？
- [ ] STATE.md 的 `updated` / `head` / `done` / `next` / `blocked` 都写了？
- [ ] `next` 只有一条，且可直接执行？
- [ ] `待拍板` ≤ 1 条？
- [ ] 没有替李广回答任何门禁？
- [ ] 没有把机械改动与行为改动混在同一提交？

## 10. 常见借口与反驳（出现即违规）

| 借口 | 反驳 |
|---|---|
| "顺便把 X 也改了" | 顺便 = 两个意图塞进一个提交，回退粒度被破坏 |
| "内容还有一点就写完了，一次出完" | 判据是**结构**不是手感：本节的结构目标完成了吗？完成就停，没完成就继续——但不许用"就一点"来跳过停机 |
| "这个改动很小，不用跑验证" | 没有验证命令的步不是步，是"我猜"。至少跑一条能失败的检查 |
| "用户没说话，我继续往下推进" | **停机是默认，不是等指令**。继续 = 制造未审阅的产出 |
| "STATE.md 我记着，不用写" | 记忆不跨会话。不写 = 断言"这次不会中断"，而它一定会 |
| "先写完，文档最后补" | STATE.md 不是文档，是恢复介质。补写 = 让下个会话在错误输入上工作 |
| "先把半成品留着，下步补完" | 允许，但必须 `wip:` 提交 + 在阻塞项显式登记，不能静默悬空 |
| "验证失败了但影响不大" | 失败即阻塞。降级要记账：能力 / 原因 / 替代手段 / 恢复条件 |
| "这一步很长但中间不用停" | 那它不是一步，是两个节。用 §2.4 四问判，不用篇幅判 |
| "我把它压短一点就合规了" | 压短 = 删内容和论证。v1 的预算表正因此被废止（§2.1）。**质量优先于长度** |
| "恢复时我就顺手把那点活干了吧" | 恢复会话只对齐不产出。顺手干活 = 跳过确认门 |
