## 图例体例

- **结构类**（流程 / 决策树 / 时序 / 节点依赖）→ Mermaid 内嵌正文；
- **具象类**（内存布局 / 指针关系 / 对象状态）→ 手写 SVG 存 `docs/assets/`，
  正文用 `![](assets/xxx.svg)` 引用。**不要把 SVG 源码直接贴进正文**——GitHub 会过滤内联 `<svg>`。
- **本项目不做动图。** 这是相对参照实例的一处体例改动：GIF 必须逐帧栅格化才能合成，
  会为一张图拖进 `rsvg-convert` + `Pillow` 两项非系统默认依赖；而它表达的「一段时间里的状态变化」，
  Mermaid 时序图或多帧静态 SVG 已能覆盖。**图全部是矢量，不需要任何栅格化。**
- 硬约束：**主线每篇 ≥ 1 图**；**全库平均 ≥ 1 图 / 200 行**。

## 状态

- **进行中**：正文 **9 / 10 篇**（`01-诞生背景` / `02-不用它的代价` / `03-谱系` / `04-代码对比` / `05-业务场景` / `06-生命周期负债` / `07-语言演进` / `08-边界` / `09-真实项目案例`）；`code/`、`docs/assets/`、`notes/` 均已建
- 学习大纲已过拍板（2026-09-30）：**谱系取宽口径** —— 回调列表 → 观察者 → 发布订阅 → 事件总线/响应式流，四层
- 第 3 节回源结论：**前三层共线**（解耦项数 0 / 1 / 3，斜率由「名单放在哪」决定），**第四层的两个名字不在同一根轴上** —— 事件总线是退回进程内换路由，响应式流是加第 4 维（速率）
- 第 4 节实测结论：**四层用代码把刻度占满 0 / 1 / 2 / 3**（事件总线的「2 项」由代码坐实，不再只是推论）。三条度量：① 发布方返回 3 次而接收方跑 0 次（`pending=3 dispatched=0`）；② 只有「自己持有名单」的那一层数得出人数；③ 加第二种事件时，只有观察者层被编译器拦下（点名 2 个既有接收方）
- 第 5 节实测结论：**三个真实系统（Qt signal/slot / 内核通知链 / inotify）的落点全在刻度 2 与 3**，0 / 1 一个都没有 —— 因为它们都是「必须让第三方不改源码就接入」的框架。两条反直觉：内核通知链的回调**返回值能中止链**（混入责任链语义）；inotify 对过载**丢弃 + 通告 `IN_Q_OVERFLOW`**（与响应式流的背压相反）。三个系统**没有一个**给调用方「数出人数」的接口
- 第 6 节实测结论：**三种坏账，工具只抓得到两种** —— 悬垂（`heap-use-after-free`）与引用环（LeakSanitizer）一加 `-fsanitize=address` 就报；而**「遍历名单的过程中名单被改」两遍输出逐字节相同**（脚本用 `cmp` 判），因为它坏的是协议不是内存。顺带坐实第 4 节 `Publish` 里那份快照拷贝买的是「注销从下一轮生效」这个可写进文档的语义。内核选了第四条路：**链内禁止注销**，并把四种通知链的锁策略与价格摆开
- 第 7 节实测结论：**三代接口形状的运行输出逐字节相同**（`cmp` 判）⇒ 差异全在编译期。7 反例 × 3 代矩阵里 **第 2 代与第 3 代逐格判定相同** —— concepts 不增加检查，只把错误指回约束声明（`api:77` vs 调用行）。最严的一格属于**虚基类**：`override` 检查签名，所以「参数收窄」「返回值不符」只有它拦得住；可调用性判据（`std::invocable` / `std::function` 构造）只问能否调用。类型擦除的账：`sizeof(std::function<void(double)>)` = 32 字节、捕获超 16 字节即落堆、生产者类体里的接收方类型名 4 次 → 0 次
- 第 8 节实测结论：**六种形态跑同一份场景**（`code/08_boundary/`），与基线的首次可见差异分别落在 **第 1 / 从不 / 2 / 4 轮**。最硬的一条是「从不」—— **`ChangeManager` 形态与基线逐字节相同**（名单搬到中介，行为一点没变）⇒ 有一种「像」跑不出来，判据必须是结构判据。第二条：GoF 自己写 `ChangeManager is an instance of the Mediator pattern` ⇒ **两个名字可以同时成立**，取决于你看哪个对象。中介者买到的其实是「合并」而不只是「解耦」（一个观察者看两个 subject 的一次事务：2 次通知 → **1** 次）
- 第 9 节实测结论：**四个真实项目，四种放法**（Qt 5.15 / Boost.Signals2 1.83 真编真跑，Linux 6.8 通知链 / Fast-DDS 3.6.2 就地摘引）。三条：① **没有一个是「发布方私有名单」这个教科书形状** —— 两端共享（Qt）、挂信号对象（Boost）、全局静态链（内核）、根本不要名单（Fast-DDS 一个实体最多一个收听者）；② 「通知遍历中改名单」分两派 —— Qt/Boost **允许**（引用计数＋延后释放，连在槽里直接 `delete` 兄弟都不崩），内核**禁止**并把禁令写进头文件；③ Boost 的弱引用是 **any-of**：一个槽跟踪两个对象，死一个全废（比 §6 说的更细 —— 忘不掉的粒度是「槽」不是「对象对」）。另收窄 §5 一句：可数性不是「一致缺失」，**取决于名单挂在有主人的对象上还是全局结构上**。价格实测：一次 `connect()` 稳定后 Qt **2** 次堆分配 / Signals2 **4** 次；一次 `disconnect()` Signals2 还要倒贴 2 次分配。
- 专题篇走向（第 9 节回源结果）：**A01 候选 = Boost.Signals2 的连接体** —— 本机可读全部实现、可真编真跑、且直接就是第 6 节那张「谁让借据作废」表的唯一忘不掉那一行；检验篇仍暂不预设
- 协作方式：小步快走，一问一答；一轮推进一个节，完成即停
